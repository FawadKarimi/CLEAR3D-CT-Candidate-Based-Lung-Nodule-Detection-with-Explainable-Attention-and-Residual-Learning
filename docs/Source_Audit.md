# Read-only source and annotation linkage audit

`audit-source` diagnoses an existing LIDC3D header inventory against a SQLite annotation database. It does not reconstruct volumes, resolve ambiguous slices, create labels or exclusions, freeze a cohort, generate candidates, release tests, or train a model. Every run sets `source_approved: false` and `training_released: false`. A completed audit means diagnostic operations completed, including the recording of unresolved findings. It is never source approval. Research audit and any slice-selection policy need separate review.

The module is independent of ConsenDxFormer and LungDxFormer. It uses neither their code nor their derived artifacts. The installed annotation database is an input to inspection, not an approved replacement for the thesis XML reference standard. Neither annotation IDs nor annotation counts are treated as reader identities or distinct nodule counts. Reader identity and coverage of small-nodule and non-nodule annotations remain explicitly unresolved; no negative labels are created.

## Invocation and safe operation

Use a new output directory outside the raw data, annotation database/package, configuration, and code/package source trees. The command accepts the existing `inventory` JSON shape (`source_root`, `slices`, `errors`) without requiring a regenerated or fully hashed archive. Every inventory DICOM path must be absolute and resolve strictly beneath the resolved `source_root`. All paths are validated before any DICOM is opened or hashed. Any `..` path component is rejected, including a traversal that would return inside the root. Direct outside-root paths and file/directory symlinks resolving outside the root fail preflight with `Raw-source boundary violation`; no output directory is created. Contained symlinks are allowed. The boundary is checked again immediately before each inspected-file read, and that contained resolved path is used for the read and hashes. Path containment checks inspect filesystem metadata, not DICOM contents. Use `configs/source_audit.yaml`, not the training reference configuration. Relative CLI arguments resolve from the recorded working directory.

Proposed university server invocation — **NOT EXECUTED**:

```bash
cd /experiment-storage/chaidir/fawad-dsai/LIDC3D
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH="$PWD/src" \
  /experiment-storage/chaidir/env/env-310-fawad/bin/python -B -m lidc3d.cli audit-source \
  --inventory artifacts/inventory.json \
  --annotation-db /experiment-storage/chaidir/env/env-310-fawad/lib/python3.10/site-packages/pylidc/pylidc.sqlite \
  --pylidc-source-root /experiment-storage/chaidir/env/env-310-fawad/lib/python3.10/site-packages/pylidc \
  --config configs/source_audit.yaml \
  --out artifacts/source-audit-v3-new-run
```

The installed console-script equivalent is `lidc3d audit-source` with the same options. `--pylidc-source-root` is optional for generic diagnostics but required to enable legacy crosswalk classifications. The source-tree invocation avoids installing/upgrading the project or changing shared packages. `-B` and `PYTHONDONTWRITEBYTECODE=1` suppress Python bytecode-cache writes, including in package trees. No pylidc import, pylidc configuration read/write, loader call, installation modification, or global NumPy patch occurs. Package versions are obtained through distribution metadata, without importing PyTorch or pylidc.

The observed server PyTorch 2.3.0+cu121 is below this project's declared `torch>=2.4` dependency. This is a separately reported environment incompatibility; nothing here changes the constraint or upgrades that environment. The audit itself imports NumPy, pydicom and PyYAML, plus Python standard-library modules, and does not use PyTorch. The reported server Python 3.10.17 / NumPy 2.2.6 / pydicom 3.0.2 / pylidc 0.2.3 combination was **not tested** in this implementation task.

SQLite is opened via a file URI with `mode=ro`, `query_only=ON`, `trusted_schema=OFF`, memory temporary storage, and a read transaction. Existing WAL, SHM or journal sidecars cause failure; use a quiescent source and have its owner handle any recovery separately. The audit does not recover or clean a database. The recorded database hash is recomputed from the actual input; the previously observed `995989985bb17106808c40572ccac2ce0b6434b91283d4f773cdb967d47443cb` is context, never a hard-coded acceptance criterion. Previously reported counts and patients are likewise not acceptance rules.

The output directory must not exist (including a dangling symlink). The tool checks lexical paths, resolved paths and resolved ancestors and protects the raw root, all inventoried DICOM parent directories and their resolved targets, the database's parent, the configuration's parent, the LIDC3D source tree, Git metadata, Python package/stdlib trees, and additional absolute `protected_roots` in the audit configuration. Every artifact uses exclusive file creation. Git status uses `--no-optional-locks` to avoid index refresh writes. Inventory, database, and configuration hashes are compared before/after. Hashing `inventory.json` establishes byte immutability of that JSON during the audit; it does **not** cryptographically verify the DICOM files it references. Only inspected repeated-position DICOMs are hashed before/after their reads. Concurrent writers are unsupported: final hashes detect persistent input changes but cannot prove absence of transient changes that are reverted. Path checks do not provide a security boundary against a hostile concurrent symlink replacement. Read-only mount/permissions and a quiescent source remain useful operating conditions.

Normal CLI execution prints three summary lines; preflight exceptions print two. Successful diagnostics exit 0 even with ambiguous links, conflicting images or captured read/decode warnings; those findings block inspected-source verification as described below. Decoding/read/schema/integrity failures, inspected inventory contradictions, invalid inclusion values, changed inputs, and artifact write failures exit 1. Details belong in files. Unsafe/existing output, unreadable initial inputs, raw-source boundary violations found during inventory preparation, or invalid configuration fail before output creation. Failures after safe directory creation normally retain all five artifacts with `audit_status: failed`; JSONL files can contain partial findings. Disk/write failures or process termination may leave an incomplete set. `audit_summary.json` is written last; absence of it or any of the other four artifacts is never completion. Do not retry into a partial directory.

## Diagnostic rules

All tolerances are explicitly required and recorded in provenance. Defaults: repeated full position componentwise absolute tolerance `1e-6 mm`; LPS z absolute tolerance `1e-4 mm`; orientation absolute tolerance `1e-4`; in-plane spacing absolute tolerance `1e-6 mm`; in-plane drift `0.1 mm`; slice spacing absolute tolerance `0.1 mm` plus relative `0.01`; HU absolute tolerance `1e-6` with relative tolerance zero. Values must be finite and nonnegative; orientation tolerance must be less than 0.1 to support a nondegenerate normal. These are diagnostic settings and do not amend ingestion or define acceptance/release criteria.

Identity comparisons use exact patient/study/series strings in both directions. Differences are also reported at patient and patient/study levels. Duplicate database identities and SOP UIDs are retained and reported. No series or slice is selected or excluded.

Every series, including equal-count series, compares all database zval rows against all finite CT LPS z values. Each zval lists every CT record within tolerance; the reverse uncovered CT list is also recorded. Sorted multisets compare multiplicity when counts agree; agreement is diagnostic, not unique identity. Duplicate scan identities are compared separately rather than merged into a fictitious scan. DB-only and CT-only series remain visible.

`ImagePositionPatient[2]` (LPS z) and `dot(ImagePositionPatient, normal)` are distinct output fields. The normal is the normalized cross product of the two DICOM orientation vectors. Database z-values are compared only to LPS z. Nonfinite/invalid position, invalid/nonorthonormal orientation, nonaxial geometry, variable orientation/spacing/dimensions, localizers, in-plane drift and irregular spacing are flagged; no reconstruction or fallback sort is attempted. Geometry for the full archive comes from inventory headers. Frame count and pixel encoding are validated only on repeated-position files because those fields are not in the existing inventory contract.

Repeated positions use all three LPS components within the configured absolute tolerance. Groups are connected components, preserving tolerance chains; a component spanning more than tolerance on any axis is explicitly `tolerance_chain_ambiguous`. Sharing only z does not create a repeated-position group. The group and member ordering never selects a preferred image.

Only these groups are decoded. Each member retains original/resolved file paths, before/after SHA256, SOP/identity, spatial tags, InstanceNumber, available acquisition/reconstruction identifiers, rescaling, padding, encoding, warnings, and errors. Missing tags are JSON null. Raw decoded arrays are compared exactly and independently of rescaling. Padding masks exclude the inclusive interval from PixelPaddingValue to PixelPaddingRangeLimit (either direction). Padding-mask equality is separate from raw equality. HU is computed in float64 from an explicit finite positive slope and finite intercept, using CT HU when RescaleType is absent; a non-HU type or LUT/real-world mapping is unsupported. HU comparison uses only the intersection of valid pixels and records its size and maximum absolute difference. Unequal validity masks can coexist with equal HU over that intersection. Empty intersections, errors, or unsupported transforms yield null comparisons, never a vacuous equality. No averages, replacements, or choices by InstanceNumber/file order/contour similarity are made.

All Python warnings captured while opening a DICOM, accessing tags, or decoding/rescaling pixels are preserved under `warnings`. WARNING-or-higher records from the pydicom logger are also retained in `pydicom_log_warnings` with their levels and messages. There are **no harmless-warning exceptions**. Any captured warning blocks the strongest inspected-source status. Warnings alone do not make the operation fail; the audit may complete diagnostically with both approval flags false. The temporary logging handler is removed after each inspection.

Inspected member evidence requires a successful source open, complete decoding/rescaling, unchanged before/after hashes, matching patient/study/series/SOP/position and other checked inventory metadata, supported geometry, and no captured warnings. Actual group geometry is checked from the opened DICOM tags as well as from the inventory. Every raw-pixel, padding-mask and valid-HU comparison in the group must be available and equal; false or null comparisons block the involved members. An unresolved tolerance chain also blocks the group. Any remaining uncertain peer blocks otherwise clean members too, because the group comparison depends on that peer. Blockers are recorded per member; no warning-free, decodable, majority, or matching member is selected as preferred. Even when all members have complete consistent evidence, their group remains `unresolved_no_slice_selected`.

## SQLite schema and linkage

The actual `sqlite_master` schema and required-table `PRAGMA table_info` are recorded on each run. Required ordinary tables are `scans`, `annotations`, `contours`, and `zvals`, each with a sole `id` primary key. The supported columns/affinities are:

- `scans`: integer `id`; text `patient_id`, `study_instance_uid`, `series_instance_uid`, `sorted_dicom_file_names`.
- `annotations`: integer `id`, `scan_id`.
- `contours`: integer `id`, `annotation_id`; integer/boolean `inclusion`; real/float/numeric `image_z_position`; text `dicom_file_name`.
- `zvals`: integer `id`, `scan_id`; real/float/numeric `val`.

Extra columns are preserved in schema metadata and do not imply supported reader/coverage semantics. Views or virtual tables cannot replace required tables. `quick_check` plus explicit identity/value/orphan checks guard the used data. Contours are left-joined to annotations and scans so broken relations cannot disappear through an inner join. Orphans, invalid scan identities, and invalid zval/contour z values fail the audit while preserving rows and findings in provenance and diagnostic artifacts. Malformed identities sort deterministically without dropping null values. Orphan annotations/zvals retain their complete queried rows in integrity findings; orphan contours also receive linkage rows and an explicit orphan-context series row. Unsupported structural schemas may prevent further row processing.

Provider source provenance now records the declared and resolved root, before/after SHA256 and immutability for `Scan.py`, `Annotation.py`, and `Contour.py`. `installed_pylidc_source_inspected` means bytes were fingerprinted only. No code is parsed, imported or executed, including SQLAlchemy. Missing/unreadable required files, escaped file symlinks, changed targets or changed bytes invalidate provenance and fail the artifact set. Escaping targets are not hashed. Lexical and resolved provider roots are protected against output placement, including aliases. The distribution version comes from `importlib.metadata` for the current interpreter; it does not authenticate the user-supplied root. There are no hard-coded provider hashes or behavior approvals. As with DICOM boundaries, use a quiescent filesystem; transient reverted mutations and hostile concurrent path changes are outside the guarantees.

Each contour preserves `dicom_file_name`, `image_z_position`, and `inclusion` under `original`, including null/unusual values. Candidate lookup is scoped to the matching patient/study/series. Filename candidates require the **entire unchanged string** to equal an inventoried basename, absolute path, or raw-root-relative POSIX path. Literal SOP candidates require the entire unchanged string to equal an inventoried SOP UID. The tool does not remove `.dcm`, parse a filename as a UID, normalize case, strip directories, or use fuzzy/similarity matching. Filesystem names and literal UIDs remain separately attributed candidate sets. A missing exact link is not repaired using position.

Literal classification precedence (mutually exclusive statuses; these six exact-evidence states take precedence over the crosswalk even when the crosswalk disagrees):

1. `filename_position_contradiction`: an exact candidate's inventory or inspected LPS z lies outside the contour's finite z tolerance; retain every candidate. The actual inspected position is compared directly to contour z to avoid adding two tolerances together.
2. `ambiguous_exact_link`: multiple exact candidates, duplicate database identity, or a nonunique SOP UID anywhere in the inventory. Position never breaks the tie.
3. `exact_link_geometry_unresolved`: exact evidence exists but contour z or series geometry cannot support the positional check.
4. `exact_link_inspection_unresolved`: exact evidence exists for a re-read file with an inspection blocker (identity/hash/read/geometry error, warning, conflicting/unavailable pixel comparison, tolerance chain, or uncertain peer).
5. `verified_inspected_source_link`: exactly one candidate in exactly one database scan context, unique SOP UID, compatible contour/inventory/actual position, supported geometry, and an actually opened source whose inspection and group comparisons have no blockers. This limited contour-to-file verification neither authenticates original XML provenance nor resolves which repeated-position slice should be used. Database zval alignment remains a separate diagnostic finding.
6. `exact_inventory_record_link_source_not_rechecked`: unique exact linkage with compatible inventory geometry and contour z, but the underlying DICOM was not opened during this audit. This is the ordinary-slice status, never inspected-source verification.
7. With no literal exact candidate, use the crosswalk status below unless it is `crosswalk_unavailable`.
8. If crosswalk evidence is unavailable, use `z_only_inventory_link` when at least one contour-z inventory candidate exists, otherwise `missing_link`. This generic fallback stays distinct even if exactly one candidate exists or a candidate happened to be inspected.

`exact_inventory_record_id` is populated only for the two concordant exact-link statuses (5 and 6). `verified_inspected_record_id` is populated only for status 5. All candidate IDs remain available for unresolved statuses, with inspected-candidate blocker details under `exact_candidate_inspections`. Per-series and global status counts use these exact names; no combined count implies source verification for ordinary records.

Every repeated group reports `neither`, `one`, or `multiple` separately for exact candidate members, crosswalk candidate members, and **verified inspected** members (`verified_inspected_members`, `verified_inspected_member_cardinality`). Per-contour reference details use `verified_inspected_record_ids`. Z-only candidate members remain separate. “Neither” means no such reference under these rules, not absence in XML. Colliding filenames, pixel conflicts and warnings can yield multiple exact candidates but zero verified inspected members. These fields do not establish reader/nodule counts or a preferred slice.

## Database-internal legacy filename/z crosswalk

The reported provider `Annotation.visualize_in_scan()` uses comma splitting and `fnames.index(c.dicom_file_name)`, while `Scan.slice_zvals` sorts numeric z values. These are supplied server observations, not behavior inferred by this tool from provider code. Legacy database names may belong to the original ingestion naming scheme and need not equal SOP-UID archive filenames. The audit does not derive SOP UIDs from those names.

Each scan preserves the original list text and splits on the exact comma delimiter. There is no trimming, case folding, numeric filename parsing, renaming or fuzzy matching. Empty tokens, duplicate names, count mismatches, invalid scan identity and nonfinite zvals invalidate the index mapping. Finite zvals are ordered by numeric `(val, id)`; the ID only makes equal values deterministic. Counts compare filenames with **all** scan zval rows, with finite and invalid counts/evidence also retained. Equal z-values leave affected indices positionally ambiguous; ID order never resolves them. Unaffected indices remain eligible for crosswalk diagnostics.

Contour lookup is scoped to its joined database scan and patient/study/series. Every exact legacy index is retained. A unique index pairs with the corresponding numeric zval and directly compares contour z minus paired z using `z_atol_mm`. Inventory candidates use the paired z in that same series and retain **every** match within tolerance, including conflicting or identical repeated slices. Invalid mappings retain indexed hypotheses for diagnosis; their candidates are not claims of valid linkage. No ordinary DICOM is opened by the crosswalk.

The nested `crosswalk.status` is always computed separately from `literal_linkage_status`. It uses this first-match precedence:

1. `crosswalk_unavailable`: no initially complete provider fingerprints, no joined scan, or nontext filename list. Generic fallback is allowed; candidate hypotheses and the reason remain visible.
2. `crosswalk_filename_nonunique`: the contour string occurs at multiple indices.
3. `crosswalk_index_count_mismatch`: filename/zval counts differ.
4. `crosswalk_invalid`: remaining scan mapping failures (including empty names, duplicate names elsewhere, invalid identity or nonfinite zvals).
5. `crosswalk_filename_missing`: no exact legacy index (including null/empty contour names).
6. `crosswalk_paired_z_ambiguous`: the matched index belongs to equal database zvals.
7. `crosswalk_invalid_contour_z`: contour z is not finite.
8. `crosswalk_contour_z_contradiction`: direct signed delta exceeds tolerance.
9. `crosswalk_z_inventory_missing`: no inventory candidate at paired z.
10. `crosswalk_z_inventory_ambiguous`: more than one inventory candidate at paired z.
11. `crosswalk_inspected_group_ambiguous`: a unique z candidate belongs to an inspected repeated-position group (possible when z tolerance is tighter than repeated-position tolerance). Full group membership is retained under `intersecting_repeated_position_record_ids`; it cannot authenticate a literal source identity, choose a member or award inspected verification.
12. `crosswalk_identity_ambiguous`: duplicate database identity or globally nonunique candidate SOP UID.
13. `crosswalk_geometry_unresolved`: inventory geometry is unsupported.
14. `database_legacy_filename_z_crosswalk_unique_inventory_link_source_not_rechecked`: one inventory target with valid scan mapping, unique index, concordant contour z and supported inventory context, whose DICOM was not rechecked.

These statuses are mutually exclusive, but all underlying findings/candidates remain available even when an earlier state wins. `crosswalk_inventory_record_id` is populated only when the top-level status is the final crosswalk success. Crosswalks never populate `exact_inventory_record_id` or `verified_inspected_record_id`. `literal_crosswalk_candidate_disagreement` records nonempty candidate-set disagreement; it does not override literal precedence or resolve a conflict. `all_candidate_record_ids` includes all literal, contour-z and crosswalk candidate hypotheses. Summary crosswalk counts cover every nested status, including zero counts and contours with literal precedence; top-level linkage counts are separate.

This ordered crosswalk is stronger than generic z-only coincidence because it checks exact scan-scoped database filenames, index/count validity and direct contour-z agreement. It remains weaker than original XML/SOP provenance and says nothing about ordinary-file hash integrity. Evidence is **provisional until** the final summary is completed and `provider_source.status` is `valid`; a changed provider file fails the whole set even if earlier streamed rows contain success classifications. Consumers must check all five artifacts and the final marker, not individual JSONL rows in isolation. Omission of the root explicitly gates crosswalk classifications off; initial missing/invalid files also gate them off and fail the run.

The reported lower-InstanceNumber duplicate-removal policy in `Scan.load_all_dicom_images()` is **not adopted**. No loader is run, and neither file order, SOP order, pixels nor majority logic selects a candidate. Every repeated group remains unresolved, including the reported one pixel-identical group. The reported 13 groups are not an acceptance constant: a server replay must reproduce their count and retain every member. XML coverage, reader identity, non-nodule marks and small-nodule completeness remain unresolved.

## Artifact schema version 3

This extends schema v2 at base `5b64f445a831c6870bb9ad7359465da7d8304641`. The diagnostic configuration remains schema version **1**, with unchanged tolerances; output and configuration schemas are independent. Schema-v2 artifacts remain historical. Do not reinterpret v2 `z_only_inventory_link` as crosswalk evidence. Regenerate v3 artifacts in a new output directory. **No in-place migration** or automatic upgrading of evidence is provided. Legacy consumers must branch on `schema_version`. Historical v1 `verified_exact_inventory_link`/`verified_record_id` must likewise never be promoted to inspected-source evidence.

All five files are required. JSONL objects each carry `schema_version: 3`; the two JSON documents carry the same field. Numbers are finite JSON numbers; unsupported nonfinite input values are retained as `{"nonfinite": "nan"}` (or the corresponding infinity string). Null comparison results mean unavailable, not false or equal. Record IDs are 1-based ranks of canonical inventory rows sorted by identity, source path, SOP UID and canonical row content; they identify inventory records, not selected slice indices.

- **`audit_summary.json`**: final `audit_status` (`completed`/`failed`), always-false approval/release flags, fixed coverage limitations, counts, bidirectional identity differences (arrays of exact identity tuples), duplicate SOP and database identity registers, preserved inventory errors, contour classification counts, per-member `inspection_blocker_counts`, and operational errors. `crosswalk_status_counts` includes every nested state, including zeros; `crosswalk_scan_finding_counts` counts scans with each of invalid identity, nontext list, empty token, duplicate filename, filename/zval count mismatch, nonfinite zval and equal zvals. `crosswalk_scan_validity_counts` separates valid/invalid index mappings and fully unambiguous scans. `provider_source_status` records the final provenance gate. Database annotations/contours/zvals and inspected DICOM records are counted separately. Inventory errors remain findings and limit completeness, even if this diagnostic run completes.
- **`series_audit.jsonl`**: one row per union patient/study/series identity, including orphan contour contexts. `identity`, `identity_status`, `ct_count`, all `database_scan_ids`, annotation count, linkage counts, repeated-group IDs, duplicate SOP IDs; `geometry` contains status/findings and every record's source path, SOP, full position, LPS z, normal and projection; `z_comparisons` contains each scan ID's CT/DB counts/delta, sorted-multiset flag, all finite zval candidate lists, invalid zval rows, uncovered CT/zval IDs and ambiguous zval IDs. `database_crosswalks` preserves each scan's original list text, ordered tokens, filename-to-index lists, counts, numerically ordered finite zval rows with IDs/values, invalid rows, equal-z groups/indices, mapping validity, findings and evidence scope. Indices are zero-based. CT-only series have an empty scan list; DB-only scans retain their complete crosswalk diagnostics.
- **`duplicate_positions.jsonl`**: one row per repeated full-position connected component. `group_id`, `identity`, `position_span_lps_mm`, tolerance-chain flag, unresolved resolution, `members` with metadata/hash/read/decode evidence, `source_opened`, captured warning lists, `inspection_blockers` and `inspected_group_geometry_findings`; `pairwise` with record-ID pairs, raw/padding/HU equality (boolean or null), common valid count, max HU difference and comparison status; `annotation_references` with all matching contour IDs, annotation IDs, inclusion flags, candidate/verified-inspected member IDs and cardinalities. Member IDs join to the series position records.
- **`contour_linkage.jsonl`**: one row per joined contour in a schema-valid database. `contour_id`, `annotation_id`, `scan_id`, `identity`, unchanged `original` fields, separate filename/literal-SOP/z candidate ID lists, their union with crosswalk candidates, contradictory candidate IDs, identity-ambiguity flag, classification `status`, nullable `exact_inventory_record_id` and `verified_inspected_record_id`, exact-candidate inspection/blocker evidence, inclusion validity and unresolved reader identity. `literal_linkage_status` retains the original evidence classification. `crosswalk` holds the unchanged legacy string, scan ID, all matched indices and unique index or null, unique paired zval row or null, signed contour-minus-paired-z difference, every per-index candidate hypothesis, all paired-z inventory IDs, index/zval/inventory cardinalities, mapping findings, status and scope. Structural schema failure may leave this file empty; relational/value failures retain rows when processing remains possible. Final summary status controls completeness and validity.
- **`provenance.json`**: UTC start/end, status, exact invocation and cwd, full audit configuration, Python/platform/package versions, SQLite mode/schema/columns/integrity findings with affected rows, protected paths, each input path and before/after hash/unchanged flag, Git revision/dirty/status and source-file hashes, explicit `inventory_hash_scope`, limited `dicom_hash_scope`, `source_boundary_policy`, `warning_policy`, provider byte-fingerprint records under `provider_source`, and the always-false loader/import flag, plus hashes of the three JSONL files. Git unavailable is recorded as null plus an error rather than an invented clean revision. The summary is written after provenance as the final marker.

Order is deterministic for identical inputs: canonical JSON identity keys, then canonical record/group IDs; contour IDs order contours; numeric `(val, id)` orders crosswalk zvals (the separate general z-comparison listing uses IDs). Candidate IDs, schema objects, flags and error iteration are stable. Provenance timestamps, paths, invocation, code dirty state and hashes intentionally vary with execution/context. JSONL findings are byte-identical for reordered inventory and database insertion order with unchanged IDs, values and paths.

## Remaining limits and verification

The header inventory may be stale or incomplete. Only repeated-position files are read/hashed and rechecked against it; there is no full-archive cryptographic verification, directory rescan, XML parsing, or general header reread. Decoder and header failures remain explicit. Geometry support is conservative; oblique/tilted or varying series need separate analysis. LUT-based intensity transforms are not interpreted. The audit does not infer what the installed loader retained when generating its database, and does not prove database filename provenance or XML completeness.

Tests use synthetic uncompressed DICOMs, temporary SQLite databases and synthetic provider-source files only. They preserve the existing source-boundary, geometry, literal-linkage, warning, hashing, read-only and CLI regressions, and add numerical ordering, exact tokens, count/duplicate/nonfinite failures, candidate cardinalities, precedence, provider gating and immutability, escaped-source/output boundaries, orphan retention, determinism and migration wording. Actual file-symlink tests skip only on an OS permission/capability failure (EPERM, EACCES, ENOSYS, ENOTSUP, or Windows privilege error 1314); other creation errors fail. Directory-link tests also exercise Windows junctions when native symlink creation lacks privilege. Compressed decoder availability, production dataset scale, Linux filesystem behavior, real database variants, university paths and clinical evidence are not established by these tests. The real server v3 replay remains **NOT EXECUTED**.

Use a fresh temporary directory for each test invocation (pytest may otherwise remove an existing `--basetemp`). Actual local verification commands/results and the full review patch are delivered in the task handoff. Existing scientific modules and rejection rules remain unchanged.
